# 遥测与崩溃诊断

本文定义 Fern 收什么、不收什么、怎么收、怎么让用户看见。

写在最前面的一条：**这个应用手里的数据是最脏的一类。** Minecraft 的日志里有玩家 ID、
有含真实姓名的路径、有服务器地址、有模组打印的任意内容，启动参数里还有 access token。
一份「把崩溃日志发回来」的天真实现，等于给自己开了一个用户隐私的下水道。

所以整篇文章的结构不是「怎么把数据传上去」，是**「怎么在传之前把它变干净」**。

---

## 1. 这是两件事，不是一件

| | 匿名使用数据 | 崩溃诊断 |
|---|---|---|
| 回答的问题 | 「还有多少人在用 Win10 / Intel Mac」 | 「这次崩溃我们为什么没认出来」 |
| 频率 | 每天几条 | 几乎没有 |
| 数据来源 | 我们自己造的枚举值 | **游戏吐出来的任意文本** |
| 风险 | 低 | 高 |
| 值不值得做 | 边际 | **高** |

**分开的开关、分开的管道、分开的文案。** 把它们合成一个「帮助改进 Fern」的复选框，
是行业里最常见的做法，也是最没有诚意的做法——两者的风险差一个数量级，
用户有权只同意其中一个。

---

## 2. 立场：默认关，首次运行明确问一次

### 2.1 同类产品的位置

- **Prism Launcher**：完全不收任何遥测。GPL，社区口碑的一部分就是这个。
- **Modrinth App**：收最小化匿名数据，可以关。

Fern 的位置：**比 Modrinth 保守，比 Prism 多一点**——默认全关，首次运行用一屏问一次，
两个独立开关，两个都是「关」的状态开始。

这不只是姿态。README 里已经写了「套壳 Fern 是玩家中木马的方式」，
一个把信任写进许可条款的产品，不该在遥测上偷偷摸摸。

### 2.2 法律上也只能这样

不是保守派的洁癖，是 opt-in 本来就是唯一合规的形态：

- **ePrivacy 指令**管的是「在用户终端设备上存取信息」。一个持久的安装 id 存在用户磁盘上，
  就落在这一条里，而这一条**没有「正当利益」的绕道**——正当利益是 GDPR 的合法性基础，
  替代不了 ePrivacy 要求的同意。
- **GDPR** 意义上的同意必须是「明确的肯定行为」，所以严格说**不存在「opt-out 式同意」**。
  默认开、给个关闭开关，在欧盟是不成立的。
- **PIPL** 同理：处理个人信息要单独告知并取得同意。真正无法关联到个人的统计不在范围内，
  但一个设备级的持久 id 很难主张自己不在范围内。

结论：**默认关 + 首次明确询问 + 随时可关 + 可重置 id。** 这样做之后，
上面三部法律不再需要逐条论证——因为拿到的是真同意。

## 3. 匿名使用数据

### 3.1 只收能改变决策的

判据只有一条：**这个数字变了，我们会做不同的事吗？** 答不上来就不收。

| 收 | 会改变什么决定 |
|---|---|
| OS + 架构 + 版本号 | 什么时候能丢掉 Win10 / Intel Mac / 32 位；哪个版本的用户还没升上来 |
| 下载源（官方 / BMCLAPI）与成功率、平均速率 | 默认源选谁；要不要再加一个镜像。这是**现在就该有**的数字 |
| Java 版本分布与来源（自带 / 系统 / 用户添加） | 要不要内置运行时下载；预检查的默认建议 |
| 启动结果：成功 / 失败 + 失败类型 id | 预检查有没有真的挡住问题 |
| **崩溃规则命中率：每条 `crash.<id>` 命中多少次，以及「一条都没命中」多少次** | 见 §4.1，这是整套遥测里最有价值的一个数 |
| 加载器类型与 MC 大版本分布 | 优先支持谁 |
| 是不是便携模式、是不是接管了已有的游戏目录 | 这两条路径的实际占比，决定测试时间怎么分 |
| 快照功能：拍过 / 恢复过（次数，不含内容） | 恢复从来没人用的话，说明入口有问题 |

| 不收 | 为什么 |
|---|---|
| 实例名、世界名、存档大小 | 用户自己起的名字就是个人信息 |
| 装了哪些模组的清单 | 可以用来做画像，而且我们不需要 |
| 账号、UUID、玩家名、皮肤 | 显然 |
| 服务器地址 | 显然 |
| 任何路径 | 见 §4.2 |
| IP | 服务端不落地，最多在入口聚合到国家级 |
| 界面点击流、停留时长 | 我们不是在做增长 |

**内存分配**这条要单独说：知道用户改没改分配值有用（默认值合不合理），
但具体数值 + 机器内存组合起来就有一点指纹味道。收「有没有改过默认值」这个布尔量，不收数值。

### 3.2 事件模型

一条事件是 `(时间, 事件名, 少量枚举字段)`，就这样。

**字段值必须是我们自己定义的枚举或数字，不能是任意字符串。** 这条是硬约束，
写成类型：事件的 payload 只允许 `enum` / `bool` / `u64` / 有限的版本号字符串。
一旦允许自由字符串，早晚有人往里塞一个路径或者模组名，而且不会有编译错误——
这跟 AGENTS.md 里「跨语言改字段名不会有编译错误」是同一类问题，
所以也用同一种办法解决：**在 `fern-core` 里把事件定义成一个枚举，`cargo test` 检查它的形状。**

### 3.3 标识

一个随机 UUIDv4，存在数据目录里。不做硬件指纹，不读 MAC、不读机器码、不读磁盘序列号。

用户在设置里能**看到**这个 id，也能**一键重置**。重置之后旧数据留在服务端但接不上——
这就是重置应该有的语义。

**自更新的灰度分桶不用这个 id。** 它自己有一个独立的、本地生成的 0–99 随机数，
而且从不上传（见 `fern-update-design.md` §5.4）。两者刻意不共用：
共用会让「检查更新」变成一条即使关掉遥测也仍然在发送标识符的通道。

用会话 id 而不是安装 id 会更安全，代价是失去「有多少人还在用」这个数——
而那正是 §3.1 里一半问题的答案。所以用安装 id，用可重置换回一部分。

### 3.4 技术选型

| 方案 | 结论 |
|---|---|
| **自己写一个端点** | **推荐。** 事件量本来就小（每装机每天个位数），服务端一张表就够。最大的好处不是省钱，是 payload 完全由我们决定，因此**可以逐字展示给用户看**（§6）。引第三方 SDK 就永远要回答「它到底还偷偷发了什么」 |
| [Aptabase](https://github.com/aptabase/aptabase) | 开源、AGPL、可自建（.NET + Postgres + ClickHouse），有官方 [`tauri-plugin-aptabase`](https://github.com/aptabase/tauri-plugin-aptabase)，不用 cookie 不做指纹。**不想自己运维时的退路**，也是自己写之前值得先读一遍的参考实现 |
| PostHog / Countly | 为产品增长设计，功能量级和我们要的东西差一个数量级。引进来的复杂度大于收益 |
| Google Analytics 一族 | 不考虑。合规和立场上都不成立 |

### 3.5 传输

- **异步、批量、失败即丢。** 遥测绝不能阻塞 UI、绝不能拖慢启动、绝不能无限重试。
- 队列只在内存里，有上限（比如 64 条），满了丢最旧的。**绝不在磁盘上攒一个会长大的文件**。
- 退出时尽力发一次，发不出去就算了。
- 有每日上限，超了就停。
- 服务端不记 IP，原始事件保留 180 天，之后只留聚合结果。

## 4. 崩溃诊断

### 4.1 目的：闭合已经存在的那个环

Fern 已经有一套崩溃规则（`fern-core/rules/crash.toml`，从 1,605 份真实报告里学出来的），
以及一套把脏文本变成结构的解析器（`crash/parse.rs` 的 `Facts`）。

那么崩溃遥测要回答的就不是「用户崩了没」，而是**三个具体问题**：

1. **哪条规则从来没命中过？** 说明它写错了，或者那个问题已经不存在了。
2. **多少次崩溃一条规则都没命中？** 这个比例就是这个功能的完成度。
3. **那些没命中的崩溃，长什么样？** 它们直接变成下一批规则的输入。

第三条决定了要传什么：**传的是 `Facts`，不是日志文本。** 而 `Facts` 恰好已经是
「结构化 + 大部分安全」的形态了——这个功能一半的工作在写规则的时候就已经做完了。

### 4.2 传什么，不传什么

| 字段 | 传 | 备注 |
|---|---|---|
| `Throwable.class` | ✅ | 全限定类名，是纯粹的技术标识 |
| `Frame.class` / `Frame.method` | ✅ | 同上 |
| `Throwable.message` | ⚠️ **要洗** | 异常消息里经常带路径、文件名，偶尔带用户数据 |
| `ReportedMod.mod_id` / `version` | ✅ | 模组 id 是公开标识 |
| `ReportedMod.name` | ❌ | 没有额外信息量，而且是自由文本 |
| `FailedMod.file` | ⚠️ **要洗** | 是路径 |
| `FailedMod.message` | ⚠️ **要洗** | 加载器写给人看的自由文本 |
| `NativeFrame.signal` / `library` | ✅ | `EXCEPTION_ACCESS_VIOLATION`、`nvoglv64.dll`，正是要的东西 |
| `NativeFrame.frame` | ⚠️ **要洗** | 整行里可能有路径 |
| `Facts.minecraft` / `java` | ✅ | 版本号 |
| `Facts.description` | ✅ | 是 MC 自己的固定短语（`Rendering overlay`） |
| 命中的规则 id、`exit_code`、加载器类型 | ✅ | |
| **`CrashReport.excerpt`（原始文本尾部）** | ❌ **绝不** | |
| **`report_path` / `hs_err_path` 指向的文件** | ❌ **绝不** | |
| 实例 id、游戏目录 | ❌ | |

「绝不」那三条要说清楚理由：崩溃报告和控制台里可能有玩家名（`Setting user: xxx`）、
含真实姓名的路径（`C:\Users\张三\...`）、连过的服务器地址、
以及任何模组自己 `println` 出来的东西。**没有任何脱敏规则能覆盖「任意模组打印的任意内容」**，
所以对原始文本唯一安全的处理是不发。

### 4.3 脱敏（那些标 ⚠️ 的）

对自由文本做**保守替换**，替换失败就整条丢掉，不是「尽力洗一洗」：

1. 家目录前缀 → `~`；Windows 的 `C:\Users\<任意>\` → `~\`。
2. 剩下的任何绝对路径 → 只留文件名（`.../foo/bar/mymod.jar` → `mymod.jar`）。
3. 形似 IPv4/IPv6/域名 + 端口的 → `<host>`。
4. 长度超过 32 的 base64/hex 串 → `<redacted>`（token 形状）。
5. 洗完之后**如果还包含非 ASCII**，整条字段丢掉——中文最可能出现在用户名和世界名里。

第 5 条会误伤一些本来无害的消息，这是有意的：**这套规则的失败方向必须是丢数据，不是漏数据。**

### 4.4 Fern 自己崩了怎么办

上面讲的全是**游戏**崩溃。Fern 自己的崩溃是另一件事：

- **Rust panic**：装一个 panic hook，收 panic 信息 + backtrace。这个数据是干净的（我们自己的代码），
  价值也最高。**优先做这一个。**
- **原生崩溃 / WebView 崩溃**：需要独立进程收 minidump。
  [`sentry-tauri`](https://github.com/timfish/sentry-tauri) 用
  [`sentry-rust-minidump`](https://crates.io/crates/sentry-rust-minidump)（底层是 Embark 的
  `minidumper` + `crash-handler`）做这件事：把自己的可执行文件用一个特殊参数再拉起来当崩溃收集进程。

**但有一个现实的拦路虎**：`fern-ui/src-tauri/Cargo.toml` 的 release profile 现在是
`strip = "symbols"`。符号被剥掉，minidump 回来也还原不出栈。要做 native 崩溃就得保留 debuginfo
（`split-debuginfo` + 单独产物）并在 CI 里用 `sentry-cli` 上传符号——这是一整条新的发布流水线。

所以判断是：**先只做 panic hook，native minidump 排到后面**。Rust panic 覆盖了绝大多数
我们自己写出来的 bug，而 WebView 崩溃在 Tauri 里通常是内存耗尽，那个用别的办法更容易发现。

Sentry 本身（自建或 SaaS）在做到 native 那一步之前不必引入。panic 事件走和使用数据同一个端点就行。

## 5. 崩溃诊断的上报形态：不要自动发

使用数据可以在同意之后静默发。**崩溃诊断不行。**

原因是 §4.2 那张表里的 ⚠️：无论脱敏写得多好，那些字段的内容都来自我们控制不了的地方。
所以形态应该是——

崩溃之后，在已有的崩溃界面里多一个按钮：**「把这次崩溃发给 Fern」**。点它之前，
先把**将要发送的完整 JSON 原样展示出来**，可以折叠、可以复制。用户点了才发。

这带来三个好处，每一个都比「自动上报多收一点数据」值钱：

1. 用户能亲眼确认里面没有他的东西。这比任何一份隐私政策都有说服力。
2. 我们自己会被迫看到 payload，脱敏漏了会立刻暴露。
3. 这个界面和已有的 `about/diagnostics`（「版本、系统与运行环境。反馈问题时附上它。」）
   是同一个东西的两种用法——**一份能复制去贴 issue，一份能一键发回来**。
   本来就该共用一个生成函数。

## 6. 开关与界面

- **首次运行一屏。** 两个独立开关，都默认关。文案说清楚「收什么」和「为什么」，
  不用「帮助我们改进产品体验」这种话——直接写「我们想知道还有多少人在用 Win10」。
- **设置 → 关于**：两个开关；「看看发过什么」（最近 N 条，原样）；「重置匿名 id」。
- **网站上一页隐私说明**（`fern-site` 已经在了），内容和代码里的枚举一一对应。
  枚举加了一条而文档没加，应该是一个 CI 失败——和 `message_ids()` 那条契约同构。

## 7. 硬红线

违反任何一条都算 bug，不算权衡：

1. **绝不上传任何原始日志、崩溃报告、`hs_err` 文件的内容。**
2. **绝不上传路径。** 文件名可以，路径不行。
3. 绝不上传账号相关的任何东西，包括玩家名和 UUID。
4. 绝不上传模组清单、实例名、世界名、服务器地址。
5. 崩溃诊断**绝不自动发送**，必须用户在看过 payload 之后点确认。
6. 遥测**绝不阻塞、绝不重试到影响体验、绝不在磁盘上攒无上限的队列**。
7. 事件字段**绝不接受任意字符串**（枚举 / 数字 / 布尔 / 版本号）。
8. 两个开关默认都是关的，并且真的关得掉——关掉之后一个包都不发（包括「已关闭遥测」这种包）。
9. 服务端不记 IP。
10. 第三方 SDK 只在能自建、能读源码、且能确认它不额外收集的前提下引入。

## 8. 实施顺序

**P0 —— 一个字节都不发。** 把「诊断信息」做完整：一份结构化的、脱敏过的、能一键复制去贴 issue
的文本。这已经做了一半（`about/diagnostics`），补完它就能立刻解决大部分「用户描述不清问题」的痛点，
而且它是后面所有阶段的数据基础。**这一步的收益/风险比高到不做没道理。**

**P1 —— 崩溃诊断（opt-in，手动点）。** 复用 P0 的生成函数，加脱敏、加确认界面、加端点。

**P2 —— 使用数据（opt-in，静默）。** 从 §3.1 里最有用的三条开始：平台分布、下载源成功率、
规则命中率。别一次把表填满。

**P3 —— Fern 自己的 panic 上报。**

**P4（可能永远不做）—— native minidump + 符号上传流水线。**

## 9. 怎么验证

- 脱敏函数要有 fixture 测试，而且 fixture 直接从 `corpus/` 里那 1,605 份真实报告来——
  那批数据里 **224 份含有真实的家目录路径**（`C:\Users\...` / `/home/...` / `/Users/...`）。
  **跑一遍全量语料，断言输出里不出现家目录、
  不出现非 ASCII、不出现形似 token 的串。** 这是唯一能真正验住脱敏的办法，
  单独造几个测试样本验不住。
- 开关关掉时的验证不能靠读代码：**抓一次包**，确认零请求。
- 事件枚举和隐私说明文档的一致性做成 `cargo test`，参照 `message_ids()`。
