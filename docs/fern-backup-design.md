# 备份、快照与导出

本文定义 Fern 的备份模型与导出格式。实现落在 `fern-core/src/backup/`。

写在最前面的一条：**备份要么能真的恢复，要么就是一个假承诺。** 一个恢复出来打不开的世界，比没有备份更糟——用户在真正出事的时刻依赖了它。下面每一处取舍都以这句话为准绳。

---

## 1. 为什么要备份

不从「Time Machine 有哪些功能」倒推，从「玩家会怎么丢东西」正推。

| 事件 | 现在的后果 |
|---|---|
| 崩溃或断电时正在写 region 文件 | 区块变虚空，或世界打不开。MC 自带的 `level.dat_old` 只护住 `level.dat`，护不住 region |
| **改模组之后世界打不开** | 删掉一个加方块的模组，它的方块全变空气；更新一个大模组，存档结构对不上 |
| 手滑删了存档，或一条 `/fill` 写错 | 不可逆 |
| 改了一堆配置之后游戏起不来 | 想回到「昨天还能跑」的那个状态 |
| 换机器、重装系统 | 想把东西带走 |

第二条决定了这个功能的形状：**改模组是一次会破坏存档的操作，而用户完全没有这个预期。** 他以为自己只是装了个模组。所以快照的价值有一半不在定时，在**赶在危险操作之前拍的那一张**（见 §5）。

第五条是导出，不是备份，两者的目标不同（见 §8）。

---

## 2. 备什么

分界不是「这是什么东西」，是**「丢了还能不能拿回来」**。

| 路径 | 进快照 | 理由 |
|---|---|---|
| `saves/` | ✅ | 唯一真正不可再生的东西 |
| `config/`、`options.txt`、`servers.dat`、`hotbar.nbt` | ✅ | 很小，但调回去很费劲 |
| `screenshots/`、`schematics/` | ✅ | 用户自己的产物 |
| `mods/*.jar` | ✅ | 见 §2.1 |
| `resourcepacks/`、`shaderpacks/` | ✅ | 同上，逻辑一致 |
| `logs/`、`crash-reports/` | ❌ | 一次性 |
| `.fabric/`、`.mixin.out/`、地图 mod 的瓦片缓存 | ❌ | 一次性，而且常常比存档还大 |
| `libraries/`、`versions/`、`assets/` | ❌ | 可重建，且不在游戏目录里 |

单文件超过 **512 MB** 的不进快照，清单里记一条跳过说明。这是防御性上限，不是策略——防止有人往游戏目录里放一个十几 G 的东西把快照撑爆。

### 2.1 模组文件必须进快照

一个曾经的错误判断，记在这里，因为它的推理过程比结论更重要。

最初的设计是「只记清单不存 jar，恢复时按来源重新下载」，理由是省空间。两个错误：

**第一，最需要那个 jar 的时刻，恰恰是我们要删掉它的时刻。** 「改模组之前拍一张」是整个功能里最有价值的触发点，而不含 jar 的快照在这个场景里的恢复流程是：世界回来了 → 那个加方块的模组已经被删了 → 世界照样打不开。快照在它专门设计要解决的场景里失效。

**第二，成本算错了。** 对象仓库是内容寻址的，**一个 jar 只存一次**，不是每张快照一份。300 个模组的整合包第一次多占约八百兆，之后只在模组真的变动时增长——而模组变动正是我们要保护的那个事件。

来源信息（Modrinth 的 project + version、sha1）仍然记在清单里，另有三个用途：导出成 mrpack 时要给下载 URL（格式要求，也避开分发版权文件）、快照被保留策略剪掉之后清单还在、以及模组更新检查。恢复时**优先用本地对象，本地没有再按来源下载**。

成本用工程手段压，不用开关压（见 §7）。

## 3. 存储模型

```
<root>/backups/
  objects/ab/abcd…              文件内容，按 sha256 前两位分桶，全局共享
  snapshots/<instance>/<时间戳>.json.gz
```

清单：

```json
{
  "version": 1,
  "instance": "3k7m…",
  "gameDirectory": "…/instances/3k7m/.minecraft",
  "takenAt": 1786152000,
  "reason": "before-mod-change",
  "label": "装 Create 之前",
  "game": { "minecraft": "1.20.1", "loader": "neoforge", "loaderVersion": "47.1.3" },
  "mods": [
    { "file": "create-6.0.jar", "sha1": "…", "source": { "modrinth": ["create", "abc123"] } }
  ],
  "files": [
    { "path": "saves/家/region/r.0.0.mca", "size": 4194304, "mtime": 1786…, "chunks": ["…"] }
  ],
  "skipped": [{ "path": "…", "reason": "too-large" }]
}
```

四个决定：

**按文件去重，不按块。** 一个世界几百个 region 文件，一次游戏只动其中几个，按文件已经能省九成以上。按块（CDC）要实现分块算法、对象数量爆炸、恢复要拼装、GC 更复杂，换来的增量有限。

**但格式里写的是 `chunks: [...]` 而不是 `hash`。** 格式留口子，实现从简。将来真要做，最该做的也不是通用 CDC，而是 **mca 感知的分块**——region 文件本来就是 1024 个独立压缩的区块，按它自己的边界切最简单也最有效。加上去不改格式。

**对象试压后存。** region 内部已经是 zlib，再压没用；NBT、JSON、文本压得动。压不动就存原样，头上一个字节标明。用已有的 deflate，不为压缩率再引一个依赖。哈希用 sha256，同样复用已有依赖。

**写入顺序保证完整性。** 先写完所有对象，最后写清单，两者都是临时文件加 rename。**清单存在即快照完整**；断电最坏留下几个没人引用的孤儿对象，由 GC 收走。

对象仓库全局共享而不是每实例一份：复制出来的实例、同一份配置、同一个整合包的两个实例，去重收益都在这里。删快照走 mark-sweep，不需要引用计数；只回收超过一小时没被引用的孤儿，避免误删正在写入的那一批。

## 4. 性能：这一条决定可行性

5 GB 的世界，第一次快照要读完算哈希（SSD 上几秒）。但**如果每次都读全部 5 GB，「每次退出都拍」就不成立**。

解法是 rsync 与 borg 的标准做法：**`(路径, 大小, mtime)` 三元组没变，就直接复用上一份清单里的哈希，不读内容。** 于是第一次慢，之后只读真正变过的那几个 region。

这不是优化项，是分水岭。mtime 理论上会骗人，但对 MC 存档不成立；另提供一个「完整校验」的手动入口。

## 5. 什么时候拍

1. **改模组之前** —— 装、删、启用禁用、更新、导入整合包更新。自动，不问。
2. **游戏正常退出之后** —— 捕获这一次的成果，而且此时文件没被占用。
3. **启动之前**，距上次快照超过 N 小时时 —— 兜住「上次退出时崩了没拍成」。
4. **手动**，可带标签，永久保留。

一条硬规则：**游戏运行时绝不拍。** region 正在写，拍到的是半个文件，而一个坏快照比没有快照更糟。

拍完复查各文件的 mtime，变过的重拍一次；仍然在变就标记这一张为「可能不一致」，而不是假装它没事。

---

## 6. 恢复

粒度是重点：用户要的通常不是「回滚整个实例」，是「把那一个世界回到昨天」。

- 恢复整个快照 / 只恢复一个世界 / 只恢复配置
- **恢复之前自动拍一张**——否则恢复本身就是一次不可逆操作
- 支持**恢复成副本**（`家 (2026-08-07)`）而不是覆盖：既安全，也支持「我就想看看昨天的基地长什么样」
- 逐个校验哈希，对不上就报出是哪个文件，**绝不写一个坏文件出去**
- 模组按 §2.1：本地对象优先，缺了再按来源下载，两者都没有时明确告知是哪几个

---

## 7. 保留与占用

近期密、远期疏：

- 24 小时内：全留
- 30 天内：每天一份
- 更早：每月一份
- 手动打过标签的：永久

磁盘占用要报得出「快照共占 3.2 GB，其中模组 2.1 GB」，以及「删掉这个实例的全部快照能省多少」——去重之后各快照大小之和是没有意义的数。

入库时试 **reflink → 硬链接 → 复制**：支持写时复制的文件系统上第一次快照几乎不占空间，Windows 同卷 NTFS 用硬链接也不占，都不支持就退回复制。失败只是不省空间，不影响正确性。

## 8. 导出

与备份共用「什么值得带走」的知识，但目标不同：**备份是给自己、在本机；导出是给别人或另一台机器、必须自足。**

| 格式 | 用途 | 内容 |
|---|---|---|
| `.mrpack` | **互操作**：Prism、HMCL、PCL 都能导入 | `modrinth.index.json`（模组给下载 URL 与哈希）+ `overrides/` 放配置 |
| `.fernpack`（zip） | 完整搬迁 | `instance.json` + 清单 + 配置 + 可选存档 + 可选 jar |
| 世界 zip | 最常见的分享形式 | 单个存档目录 |

mrpack 价值最高，而且我们已经具备生成它的条件：模组清单里记了 Modrinth 的 project 与 version 就直接进 `files[]`，没有来源的 jar 落进 `overrides/`。**导出与导入用的是同一份格式知识**（解析那一半在 `supply/modpack.rs`）。

因为 mrpack 里的模组是 URL，别人下不到就是下不到——所以 `.fernpack` 默认把 jar 打包进去，那是「保证能用」的那一个格式。

---

## 9. 失败模式

| 情况 | 行为 |
|---|---|
| 快照期间文件被改 | 只在游戏没运行时拍；复查 mtime，变过的重拍；仍在变则标记为可能不一致 |
| 磁盘满 | 失败要干净（清掉临时文件），**绝不影响启动**——最多是一条通知 |
| 对象仓库损坏 | 恢复时校验哈希，报出具体是哪个文件，不写坏文件 |
| 用户手工删了 `backups/` | 一切照常，重新开始 |
| 模组既不在对象仓库也下载不到 | 恢复继续，明确列出缺了哪几个，由用户决定 |

## 10. 模块与顺序

```
fern-core/src/backup/
  mod.rs        对外：snapshot / restore / list / prune / usage
  store.rs      对象仓库：put / get / gc
  manifest.rs   清单读写
  select.rs     哪些路径进快照 —— §2 那张表的落地
  schedule.rs   保留策略
  export.rs     mrpack / fernpack / 世界 zip
```

`select.rs` 是地基：磁盘占用、清理、复制实例、导出四个功能都从它长出来。

落地顺序：`store` + `manifest` + `select`（能拍能列）→ 恢复 → 触发点接进模组操作与游戏退出 → 保留策略 → 导出。

**外部实例同样受用**：快照读的是游戏目录，写的是我们自己的 `backups/`。接管别人的 `.minecraft` 之后，备份是我们提供的净增量。共享布局下两个实例指着同一份存档时各拍各的，重复内容由去重消掉，清单里的 `gameDirectory` 让界面说得清那是同一份。
